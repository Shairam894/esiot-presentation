1. Introduction and learning objectives

Integration is the disciplined process of combining separately developed and verified components and checking their interfaces and interactions. Testing is the execution or analysis of a system under defined conditions to find defects and provide evidence that requirements are met.

Why it matters

An individually correct driver, task or sensor module can still fail when combined: message formats may differ, interrupts may arrive at the wrong time, buffers may overflow, or the real hardware may behave differently from a mock.

Prerequisites

C/C++, microcontrollers, GPIO, timers, interrupts, UART/SPI/I²C/CAN, RTOS concepts, state machines, debugging, requirements and basic software testing.

Learning objectives

  • Distinguish unit, integration, system and acceptance testing.
  • Compare top-down, bottom-up, big-bang and incremental integration.
  • Design tests for interfaces, timing, faults and resource limits.
  • Interpret test coverage, defect rate and pass/fail evidence.
  • Use test doubles, hardware-in-the-loop (HIL), logs and trace tools appropriately.

Key terminology

TermMeaning
VerificationEvidence that work products satisfy specified requirements: “Did we build it right?”

Core idea: integration testing focuses on the contracts and interactions between modules—not just whether each module works alone.

3. Integration workflow and strategies

  1. Plan from requirements. Identify interfaces, ownership, timing budgets, test environment, acceptance criteria and safety risks.
  2. Verify components in isolation. Unit-test functions and drivers with controlled inputs, boundary values and error injection.
  3. Stabilize interface contracts. Agree data types, units, byte order, timeouts, buffer sizes, return codes and concurrency rules.
  4. Integrate in small increments. Add one component or interface at a time; run smoke and regression tests after each change.
  5. Exercise the real target. Test compiler, linker, startup code, clock tree, memory map, peripherals, interrupts and RTOS configuration on the board.
  6. Run system and acceptance tests. Verify end-to-end behavior, timing, recovery, power, robustness and user requirements.
  7. Record evidence and release. Preserve firmware version, configuration, test logs, failures, fixes and requirement traceability.

Integration approaches

ApproachHow it worksStrengthRisk / limitation
Big-bangCombine many modules at onceSimple to describe for tiny systemsFault localization is difficult; interface defects appear late
Top-downStart at application/control layer; use stubs for lower layersEarly demonstration of high-level flowLow-level drivers and hardware issues are deferred
Bottom-upValidate low-level drivers and services first; use drivers/test harnesses aboveEarly confidence in hardware-facing componentsEnd-to-end behavior appears later
Incremental / sandwichIntegrate in planned slices, sometimes from both endsEarlier defect isolation and continuous feedbackNeeds interface planning and temporary test doubles
Practical rule: choose incremental integration for most non-trivial embedded projects. Keep each change small enough that a failure has a short list of likely causes.

4. Test levels, techniques and tools

Level 1

Unit testing

Tests one function or module in isolation. Use boundary cases, mocks and deterministic inputs.

Example: CRC routine returns expected checksum for known byte sequences.

Level 2

Integration testing

Tests contracts and interactions between modules, drivers, middleware and devices.

Example: sensor driver plus I²C HAL handles NACK and timeout correctly.

Level 3

System testing

Tests the complete product against system requirements in a representative environment.

Example: periodic sampling, radio transmission and low-power sleep work together.

Level 4

Acceptance testing

Confirms the product is fit for its intended use and acceptance criteria.

Example: field workflow meets a customer-defined data-loss limit.

Technique

HIL / SIL

SIL: software executes against simulated plant or peripherals. HIL: real controller interacts with real-time simulated inputs/outputs.

Technique

Fault injection

Deliberately introduce timeouts, corrupt packets, sensor disconnects, low voltage or queue saturation to test recovery.

5. Coverage, timing and reliability metrics

Coverage measures

Statement coverage (%) = executed statements / total executable statements × 100 Branch coverage (%) = executed decision outcomes / total decision outcomes × 100 Requirement coverage (%) = requirements with linked test evidence / total testable requirements × 100

Coverage shows what was exercised, not whether the test assertions were strong or the product is defect-free. High coverage is useful evidence, but not proof of correctness.

Timing and real-time correctness

Response time = completion time − event arrival time Deadline miss = response time > deadline Utilization (single periodic task model) U = Σ(Cᵢ / Tᵢ)

Here \(C_i\) is worst-case execution time (seconds) and \(T_i\) is period (seconds). For independent periodic tasks on a single preemptive processor, utilization is a useful load measure; schedulability depends on the scheduling policy, deadlines, blocking, interrupts and overhead. Do not assume \(U<1\) alone proves every task set meets deadlines.

Reliability and defect triage

  • Reproducibility: can the failure be repeated with a known build and setup?
  • Severity: impact on safety, function, data integrity or availability.
  • Priority: urgency for fixing, considering release risk and workarounds.
  • MTTR: mean time to repair/recover, depending on the definition used by the project.
  • Test evidence: test ID, requirement, firmware hash, board revision, configuration, stimulus, expected/actual result and log.
Do not confuse: statement coverage and branch coverage are different. A test can execute a line containing an if statement without exercising both its true and false outcomes.

6. Solved numerical examples

Example 1 — Statement coverage (Easy)

Given: 180 executable statements; tests execute 153 distinct statements. Find statement coverage.

Formula: coverage = executed / total × 100.

Substitution: \(153/180 × 100 = 85\%\).

Answer: 85% statement coverage. This says 27 statements were not executed; it does not mean the software is “85% correct.”

Example 2 — Periodic task utilization (Moderate)

Given: three periodic tasks on one CPU: \(C_1=2\) ms, \(T_1=10\) ms; \(C_2=1\) ms, \(T_2=5\) ms; \(C_3=3\) ms, \(T_3=20\) ms.

Formula: \(U=\sum C_i/T_i\).

Calculation: \(U=2/10+1/5+3/20=0.2+0.2+0.15=0.55\).

Answer: 55% CPU utilization for these task execution budgets, before unlisted interrupt and RTOS overhead. Analyze deadlines, blocking and overhead before declaring the system schedulable.

Example 3 — GATE-style pass probability (Difficult)

Given: a deterministic test suite has 40 independent test cases. A run passes 38 and fails 2. What is the observed pass rate?

Formula: pass rate = passed / executed × 100.

Calculation: \(38/40 × 100 = 95\%\).

Answer: 95% observed pass rate. The two failures still need triage. A pass rate is not a reliability probability unless a suitable statistical model and sampling assumptions justify that interpretation.

Engineering note: numerical metrics summarize evidence; they never replace reviewing failed tests, requirement coverage, risk and real-target behavior.

8. Core electronics / embedded interview questions

Try answering aloud first, then expand the concise reference answer. Strong answers connect theory to observable evidence and failure handling.

1. What is the difference between verification and validation?

Verification checks conformance to specified requirements and design artifacts; validation checks whether the finished product meets intended use and user needs. A product can pass verification yet fail validation if requirements were incomplete.

2. Why is incremental integration preferred?

It limits the number of newly introduced variables after each build, localizes interface defects and enables continuous regression testing. It does require stable contracts and temporary stubs or harnesses.

3. What is a hardware abstraction layer (HAL), and what can go wrong at integration?

A HAL presents a common interface to hardware-specific operations. Problems include incorrect pin mapping, clock configuration, polarity, alignment, timeout units, interrupt priorities or assumptions that differ across MCU families.

4. A sensor works in a unit test but fails on the board. What do you check?

Check power and ground, pull-ups, bus voltage, address and wiring; inspect waveforms and ACK/NACK; verify pin mux, clock, timing, device initialization, driver configuration and error handling. Reproduce with a minimal test before changing multiple variables.

5. How do you test a timeout or disconnected peripheral?

Use a controllable mock for logic tests, then disconnect or inhibit the real peripheral on a bench/HIL setup. Verify timeout bounds, retry limits, error reporting, resource cleanup and safe-state behavior.

6. Why can debug logging hide a race condition?

Logging changes execution time, task scheduling, interrupt latency and buffer pressure. Use low-overhead trace, GPIO timing markers or hardware trace where possible, and compare instrumented versus minimally instrumented builds.

7. Explain a test stub versus a mock.

A stub provides canned responses from a dependency. A mock can also record and assert how the dependency was called—for example, that a driver was not retried more than three times.

8. What is HIL testing?

A real embedded controller is connected to a real-time simulator that supplies sensor-like inputs and reads outputs. It enables repeatable system tests, including edge cases that are difficult or unsafe to create physically.

9. How would you test an RTOS queue under stress?

Test empty/full behavior, producer faster than consumer, multiple producers/consumers, ownership and lifetime of queued data, timeout semantics, priority inversion and long-duration operation. Monitor dropped messages and worst-case latency.

10. Statement coverage is 100%. Is the software fully tested?

No. Branches, boundary values, invalid inputs, concurrency, timing, hardware behavior and requirements may remain untested. Coverage is a guide to test completeness, not a correctness guarantee.

11. What should a useful defect report contain?

Build/version, hardware revision, setup, exact reproduction steps, expected and actual results, frequency, logs or scope captures, severity and related requirement/test IDs.

12. How do you test firmware upgrades and rollback?

Test valid and invalid images, signature/version checks where applicable, power loss during each update phase, storage exhaustion, boot selection, rollback criteria and data compatibility. Confirm the device recovers to a known bootable image.

Industry perspective

Integration and validation engineers work across firmware, board design, manufacturing test and systems teams. Typical deliverables include interface-control documents, test plans, automated test scripts, HIL rigs, traceability matrices, defect reports and release evidence. Safety-related products may require domain-specific standards and independent review; the required process depends on the application and jurisdiction.

High-priority review checklist

  • Define observable expected results before running tests.
  • Test normal, boundary, invalid, timeout and recovery paths.
  • Check data units, signedness, alignment, byte order and buffer ownership at interfaces.
  • Measure timing on the target; do not rely only on host simulation.
  • Include reset, startup, low-power wake-up and fault recovery in system tests.
  • Automate repeatable tests and keep regression tests after fixes.
  • Record exact firmware, board and configuration for every result.
